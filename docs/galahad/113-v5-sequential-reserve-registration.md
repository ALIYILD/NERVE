# V5 registration: exact numeric agreement and deterministic provenance

Status: hypothesis/specification registered; no implementation, evaluation, reserve opening or signing. Machine-readable registration: `evidence/family-b-v5-registration.json`. This is separate from Loop 46 normalization: v5 keeps the existing family-B parser and input contract.

Design inputs are the published v4 stratum counts only: format-variant agreement 7/11 and multi-source agreement 8/11, with every other stratum correct on all 11 or 12 items. No item-level journals, reserve items or labels were read. The paired incumbent is retained family-B v4 skill v1, not original family-A v1 or the earlier adapted bootstrap. The exact model digest and incumbent record hash are bound in the registration.

Frozen rule specification: select current records matching the exact query entity, mass and mg. With none, abstain. Compare every matching value using exact Decimal equality, without tolerance, unit conversion or majority vote. Any dissent requires abstention. If all agree, emit the value/unit and identity of the lexicographically smallest full supporting source ID, deterministically. Unsupported input fails closed. Decimal agreement is already implemented by the family-B adapter; its inclusion preserves behavior and is not a new improvement. The new intervention is deterministic answer/source selection instead of model provenance choice. No prompt or parser redesign is bundled into v5.

Predicted gain is confined chiefly to agreement/provenance strata. Primary regression stratum: dissenter, if equality or selection accidentally masks a real disagreement. Secondary risks are stale-vs-current and entity/measurement decoys if selection happens before strict filtering. No measured v5 accuracy exists, and the observed v4 counts are not reused as evaluation outcomes.

Evaluation is prospectively assigned to a single sequential stream over the 200 unused bank-v3 reserve items, stored in the existing slice2/slice3 containers. These storage names do not define two evaluations: no fixed-slice verdict, reset, reuse of consumed slice1 or repeated alpha allowance is permitted. A gate custodian must verify sealed hashes and nonconsumption, then commit a seed-20261017 stratified pooled schedule before observing any outcomes; item-level content stays private. This registration reads only the public manifest, not reserve contents, and does not mark anything consumed.

Proposed gate parameters preserve the existing simulation design: paired v5-v4 marginal correctness, bet 0.5, alpha 0.00025 (E threshold 4000), futility E <= 0.05, maximum 200 items, domain/stratum veto, and plateau max(3, ceil(2 * SD of three real dev-seed deltas * 200)). No seed deltas are invented. The old simulation wallet is not reusable; a dedicated research allocation is required. A threshold crossing yields a proposal only, never automatic signing. Exhaustion yields insufficient_power. No retuning after reserve outcomes is allowed.

Admission is currently blocked: the existing sequential contract explicitly accepts simulations only, has no authorized reserve adapter, and requires a deployed incumbent whereas this v4 is registry-retained but not deployed. A separately versioned research contract must explicitly bind the retained comparator without claiming deployment, validate the finite-bank/without-replacement statistical assumptions, freeze candidate implementation and schedule hashes, obtain real three-seed dev deltas and commit the wallet before any reserve access. The existing gate remains unchanged and inactive; this document does not masquerade as an accepted executable gate registration. Its earlier zero-good-accept simulation remains relevant to power, not a reason to lower thresholds after outcomes.

The v5 deterministic rule adds zero model calls on supported records. Its paired v4 comparator requires at most 200 logical calls, or 600 attempts with two identical-request retries; future dev/calibration costs need separate registration. All current work is CPU documentation/authorization validation only. Stop point: registration, with zero reserve items consumed and zero model calls.
